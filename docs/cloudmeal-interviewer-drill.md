## 一、面试官究竟在判断什么

我会用模拟面试官的标准检查你能否解释自己的项目，不要求你假装已经做成大型生产系统。

1. **真实性**：你究竟改了什么，哪些沿用了基础项目，哪些由协作工具辅助？是否能亲自定位和修改代码？
2. **理解深度**：为什么需要这个设计，删除某个条件会发生什么？
3. **边界意识**：你说的保证覆盖哪些调用路径，哪些不覆盖？
4. **故障推理**：两个线程交错、数据库回滚、进程退出、网络超时后分别是什么结果？
5. **验证能力**：用什么测试或监控证明，而不是只说“理论上没问题”？
6. **取舍能力**：为什么当前不用更复杂的技术，什么指标达到什么程度才升级？

回答采用这个顺序：**当前实现 → 保证范围 → 一个反例 → 改进方案 → 验证方法**。不要每题都从“生产环境应该上 MQ”开始。

### 训练评分（不是录用预测）

| 分数 | 回答表现 |
| --- | --- |
| 0 | 与代码相反，或把没做的说成做过 |
| 1 | 只会背定义，无法联系项目 |
| 2 | 能讲业务流程和关键代码 |
| 3 | 能推演并发/失败反例，说明保证范围 |
| 4 | 在 3 分基础上，给出可执行改进和验证方法 |

核心链路目标至少 3 分。答错时先纠正事实，不靠补几个术语掩盖。

## 二、18 组逐层追问

### 01｜“这个项目和普通外卖教程有什么区别？”

**首问**：用一分钟讲清项目，以及你自己真正负责的部分。

**继续追问**：

- 哪些是基础项目已有的？哪些是你的改造？
- 选一个改造，原来会出什么错？不是“我加了一个模块”，而是“解决了什么矛盾”？
- 如果使用 AI 或他人协助，你如何验证代码？现在能不看答案写出关键 SQL 吗？

**稳妥回答**：

> 这是在基础点餐系统上持续迭代的练习项目，不是从零独立创造所有代码。我的讲解重点是服务端计价、优惠券全链路和超时补偿；具体负责范围按实际开发经历说明。例如领取不是只加一张表，而是要同时处理库存竞争、同用户重复领取和失败回滚。我能从 Service 定位到条件 SQL、唯一索引和并发测试，解释它们各自解决什么问题。

**扣分点**：未经事实支持就说“独立从零开发”“线上百万用户”“提升 80%”。即使代码确实存在，也不能替你证明个人贡献。

### 02｜“已经加事务了，为什么领取前的 count 不够？”

**反例**：用户 A 发两个请求，二者都查到 count=0。

**继续追问**：

- `@Transactional` 是否会把两个请求自动串行？
- 库存扣减成功、插入用户券唯一键冲突，库存为什么恢复？
- 不抛异常而是直接 `return Result.error`，还会回滚吗？
- 为什么不用 synchronized？

**参考回答**：

> 普通事务并不让“先查后插”自动串行。count 是友好提示，唯一索引 `(user_id,coupon_id)` 才是并发兜底；`stock=stock-1 WHERE stock>0 AND status=1...` 负责库存。两项写操作在同一事务内，插入冲突转换成业务异常并抛出事务代理边界，库存扣减才会一起回滚。若吞异常并正常返回，就不能指望 Spring 自动回滚。JVM 锁又只能管一个进程，不能替代数据库约束。

**必须区分**：库存不为负、每用户只能领一次是两个不变量，需要两种约束。

**验证**：库存 3，多个不同用户竞争，最终成功数 3、库存 0；同用户并发，最多一条券。不能只看线程有没有异常。

依据：[领取实现](D:/canyun/houduan/sky-server/src/main/java/com/sky/service/impl/CouponServiceImpl.java)、[库存条件更新](D:/canyun/houduan/sky-server/src/main/java/com/sky/mapper/CouponMapper.java)、[表约束](D:/canyun/houduan/sql/coupon.sql)。

### 03｜“下单有事务，用户双击就不会创建两个订单？”

**错误答案**：“会，事务保证幂等。”

**继续追问**：

- 同一用户同时提交两个不使用优惠券的请求呢？
- 清空购物车是不是可靠的幂等机制？
- 请求超时后重发，如何返回第一次已经创建的订单？

**参考回答**：

> 当前没有专门的服务端下单请求幂等键，事务只保证每次下单内部一致，不保证两个请求只建一单。前端按钮防重、购物车最终清空都不是完整的后端去重协议。并发结果还受隔离级别、锁和时序影响，不能承诺永远只生成一单。
>
> 改造时引入 userId + clientRequestId 唯一约束，持久化请求与订单的对应关系；相同请求重试返回同一个结果，校验相同键不能携带不同业务内容。并发冲突后应在适当的新读边界获取已提交结果，避免一直读旧快照。进程宕机后也能从数据库恢复，不能只在 Redis 中设置一个短期标志。

**验证**：两个线程同键提交、响应丢失后重试、同键不同内容、建单成功后应用重启。优惠券防重与创建订单幂等不能混为一谈。

### 04｜“支付与取消只能一方成功，你怎么证明？”

**现场题**：写出两方 WHERE 条件，再推演支付先更新但核销失败的情况。

**参考回答**：

> 两方竞争同一订单行，前提都是待付款且未支付。支付改为待接单已支付，取消改为已取消未支付。UPDATE 是加锁操作，不是沿用最初普通 SELECT 的快照直接覆盖。某一方成功更新并提交后，另一方旧状态条件不成立。若先更新的一方在后续券操作中失败并回滚，另一方仍有机会成功。所以不是“谁先发请求谁赢”，也不是“先执行过 UPDATE 就永久赢了”。

**继续追问**：RR 下最初读到旧订单为什么不影响最终裁决？你是否依赖串行化隔离级别？

**要点**：最终更新依赖数据库加锁与条件判断，不需要为了这个状态转换把整个应用改成 SERIALIZABLE；不要把普通一致性读和 DML 混成一种读取。

**验证**：分别强制两种交错，并注入券更新失败；断言订单与券的最终组合，而不仅是某一线程返回成功。

依据：[订单服务](D:/canyun/houduan/sky-server/src/main/java/com/sky/service/impl/OrderServiceImpl.java)、[订单 SQL](D:/canyun/houduan/sky-server/src/main/resources/mapper/OrderMapper.xml)。

### 05｜“你说支付幂等，那已接单后再次支付呢？”

**代码事实**：当前仅在 `TO_BE_CONFIRMED + PAID` 时直接返回；已支付订单进入 CONFIRMED 等后续状态时，重试会被拒绝。

**参考回答**：

> 目前是演示支付的局部重试处理，并非全生命周期统一返回原支付结果。它基本防止重复进行未支付到已支付的状态转换，但不代表所有后续状态都能给出同样的成功响应。
>
> 真正的支付幂等应围绕独立支付记录、商户订单号和平台交易号建立，校验金额和归属，返回已确认的支付结果，而不是把它耦合到订单仍处于待接单阶段。订单可能已完成，但支付事实依然有效。

**致命追问**：“前端请求成功，怎么证明钱到账了？”

必须承认当前是演示支付。真实支付回调、验签、查单、退款、对账是未来方案，数据库事务无法回滚支付平台已经发生的扣款。

### 06｜“15 分钟到了是不是绝对不能支付？”

**代码事实**：定时任务每分钟扫描超时订单；支付 SQL 没有订单截止时间条件，`cancelTimeoutOrder` 自身也没再次检查订单年龄。

**参考回答**：

> 当前是扫描式超时关闭，不是严格截止时刻控制。超过 15 分钟但任务尚未关闭时，只要状态还允许，支付请求仍可能成功。服务延迟、扫描积压会让窗口更长，不能把定时扫描说成精确到秒的禁止支付。

**改进**：先明确业务规则。如果要求严格到期，持久化 `expire_time`，支付入口/状态更新校验截止时间，关闭路径也校验到期条件；真实支付还需协调支付平台订单有效期，以及晚到成功通知后的处理规则。

**再追问**：优惠券下单时没过期，支付时过期怎么办？

当前 `markUsedByOrder` 只校验绑定和 LOCKED，没有有效期判断，等于锁券后支付不再检查券到期。可以选择锁定时资格保留至订单截止时间，但必须明确产品规则并补测试，不能声称当前已在支付时重新验券。

### 07｜“WebSocket 已通知商家，但事务最后提交失败呢？”

**代码事实**：`orderpayment` 在事务方法返回前调用 `sendToAllClient`，事务提交发生在代理退出阶段。

**参考回答**：

> 当前有提前通知风险：推送不属于 MySQL 事务，提交失败无法撤回已发通知，管理端也可能先收到消息后查不到已支付状态。先改成事务提交后通知可以避免回滚前的假通知，但仍有“提交成功、进程在发送前宕机”的丢消息窗口。

**进阶方案**：订单状态与 Outbox 事件同事务提交，独立发送器重试发布，消费端按事件 ID 去重。WebSocket 仅作刷新提示，页面重新读取权威订单状态，断线重连也要补查。

**再追问**：Redis Pub/Sub 能保证补发吗？不能把它当持久化消息系统；跨节点通知和可靠投递是两件事。

**验证**：提交前异常、提交后发送失败、重复消息、断线重连。`afterCommit` 不是“保证消息不丢”的完整答案。

### 08｜“你的 REQUIRES_NEW 在当前调用链里真的挂起了外层事务吗？”

**代码事实**：`OrderTask` 本身无事务；它捕获 `cancelTimeoutOrder` 抛出的异常后才调用补偿记录方法。取消方法经过代理返回异常时，原事务已结束。

**参考回答**：

> 在当前调度调用路径里，没有仍然活动的外层业务事务需要挂起；这时 REQUIRED 也会新建事务。选择 REQUIRES_NEW 的意义是明确失败记录的独立提交语义，防止未来从其他带事务的入口调用时加入外层事务。不能照背“当前必然挂起外层事务”。外层事务回滚仍保留记录的测试验证的是另一种调用场景。

**继续追问**：如果确实在外层事务中调用，有什么代价？

外层连接和资源可能继续占用，内层需要额外连接；连接池小、并发高时可能等待。若内层访问外层已持有锁的资源，也可能产生锁等待。独立事务不是免费操作。

依据：[任务调用链](D:/canyun/houduan/sky-server/src/main/java/com/sky/task/OrderTask.java)、[补偿事务](D:/canyun/houduan/sky-server/src/main/java/com/sky/service/impl/OrderCompensationServiceImpl.java)。

### 09｜“有原子抢占，你的补偿就 exactly-once 了吗？”

**反例**：取消已经提交，但标记任务 SUCCESS 前进程宕机。任务回收后会再次执行。

**参考回答**：

> 抢占只保证同一时刻的状态竞争有一个持有者，不能保证整个任务生命周期只执行一次。故障重试要求业务可安全重复执行。超时回收也不能证明旧执行者已经停止，只表示租约过期。

**追问**：processing_time 是不是完整 fencing token？

> 当前 processing_time 主要保护补偿记录的成功/失败回写，不能阻止旧执行者继续触发业务副作用。订单条件更新和业务幂等仍不可缺少。更严谨可以使用递增 claim_version，并要求真正执行副作用的资源也校验版本；仅在任务表回写检查版本，不等于整个系统已被 fencing 保护。跨节点时间戳还受到时钟偏差和精度影响。

**验证**：人工阻塞旧执行者，回收任务、让新执行者接管，再放开旧执行者，检查业务状态和任务状态。

### 10｜“SUCCESS 和 MANUAL 就算异常闭环了吗？”

**追问一**：如果脏数据是“订单已取消、券仍 LOCKED”，补偿能修吗？

**参考回答**：

> 当前 `cancelTimeoutOrder` 发现订单不是待付款就返回，并未对所有订单—券组合做对账；补偿执行器可能随后标 SUCCESS。因此这里的 SUCCESS 只是该任务正常返回，不是任意历史脏数据已经核验修复。它依赖正常业务链路维护不变量，不能宣称是通用数据修复器。

**追问二**：补偿记录本身写失败、进程直接退出怎么办？

> 当前会记错误日志；没有记录的未付款超时订单可被后续普通扫描再选中，前提是数据库和调度恢复。还需监控未关闭订单年龄、补偿落库失败及积压，不能保证异常证据一定留下。

**追问三**：转人工以后谁处理？

MANUAL 目前主要是数据库状态，不等于已有人工工单系统。完整闭环需要告警、负责人、带审计的重试/修复操作和超时升级。也要明确 3 次是自动补偿失败上限，不包括首次取消失败或所有进程崩溃次数。

### 11｜“你说状态机一致，那商家拒单也一样安全吗？”

**代码事实**：`AdminOrderServiceImpl` 的接单、取消、拒单等路径仍有先查询再按 id 更新的实现；取消/拒单没有退款链路。

**参考回答**：

> 目前完善的是用户未支付取消、超时取消与演示支付的竞争，不能推广成“所有订单状态转换都并发安全”。管理端路径需要统一加预期状态条件，避免接单和拒单交错覆盖。对已支付订单拒单还必须设计退款状态机，不能只把业务订单改为 CANCELLED 就声称资金处理完成。

**验证**：商家接单与拒单并发；退款失败或回调重复；订单已取消但支付事实已成立。业务状态与资金状态是两条相关但不相同的轴。

依据：[管理端订单服务](D:/canyun/houduan/sky-server/src/main/java/com/sky/service/impl/AdminOrderServiceImpl.java)。

### 12｜“删缓存就一致？给我一条旧值回填的时间线。”

```text
读请求 R：缓存未命中 → 从数据库读到旧值 ─────────→ 把旧值写回缓存
写请求 W：                    更新数据库 → 删除缓存
```

写请求结束后，R 仍可能把旧值写回。因此“先更新库再删缓存”不是强一致保证，提交前删缓存的问题也不能与此混为一谈。

**参考回答**：

> 我会先明确菜单展示容忍短暂旧值，但下单必须走权威校验。当前菜品缓存有 30 分钟 TTL，是过期兜底，不代表最坏陈旧窗口足够短。事务提交后删缓存改善提交时序；延迟双删只能降低概率，不能无条件证明正确。更严格可采用版本化缓存写入、可靠失效事件、互斥重建等协议，并验证失效和回填时序。

**追加陷阱**：当前空列表虽然会写缓存，但读取时只有非空列表才算命中，仍会反复回源；光说“已经缓存空值防穿透”是错的。

依据：[菜单缓存](D:/canyun/houduan/sky-server/src/main/java/com/sky/service/impl/DIshServiceImpl.java)、[菜品修改](D:/canyun/houduan/sky-server/src/main/java/com/sky/controller/admin/DishController.java)。

### 13｜“你说 AI 支持多轮，前端把 sessionId 发到哪里？”

**代码事实**：后端接收/返回 sessionId，支持最近 20 条消息；小程序 API 目前只提交 `{message}`，页面未保存并回传 sessionId。

**参考回答**：

> 当前完成的是后端多轮基础，不是前后端完整多轮。前端每次不传 sessionId，后端就会创建新会话；页面上看到聊天气泡历史，不代表模型收到了这些历史。需要前端保存成功或失败响应里的 sessionId，在下一轮携带，并定义新建会话、切换会话、重进页面和登录切换时的清理行为。

**验证**：连续发送两次消息，检查第二次请求的 sessionId 与第一次响应一致，数据库同一会话消息递增，模型请求确实包含上一轮内容；拿其他用户 sessionId 必须失败。

**扣分点**：拿“有会话表”“页面显示历史”“写了单元测试”任意一项代替完整证据。

依据：[AI 编排](D:/canyun/houduan/sky-server/src/main/java/com/sky/service/impl/AiChatServiceImpl.java)、[小程序 API](D:/canyun/xiaochengxu-source/pages/api/api.js)。

### 14｜“为什么模型调用不放数据库事务里？放外面以后崩溃怎么办？”

**当前流程**：短事务保存提问并置 PROCESSING → 事务外检索和模型调用 → 短事务保存回答并恢复 ACTIVE。

**参考回答**：

> 外部模型耗时不可控，不应一直占数据库连接和行锁。两个短事务中间的 PROCESSING 状态防止同会话同时进行多轮调用；保存消息先锁会话行，再分配 sequence_no，因此 MAX+1 的安全依赖所有写入者遵循同一会话锁协议，并不是 MAX+1 自己原子。

**致命反例**：用户消息提交之后直接杀进程，catch 不会运行；会话可能一直停在 PROCESSING。

**改进**：加入 turnId、processing_started_at、租约/版本以及恢复任务；结果保存和失败恢复都匹配本轮 turnId。需要处理旧调用晚回来的结果，不能让它写入新一轮。请求幂等号还要防止网络超时重发后重复插入用户提问。

**额外细节**：模型失败后当前只恢复会话，已保存的用户消息仍存在。这有助保留失败上下文，但重试又插入同样消息会重复；应明确“重试旧轮”还是“发起新轮”的协议。

**验证**：保存 USER 后杀进程、供应商超时、保存 ASSISTANT 失败、恢复状态失败、旧结果延迟返回、同会话并发请求。

依据：[AI 持久化](D:/canyun/houduan/sky-server/src/main/java/com/sky/service/impl/AiChatPersistenceServiceImpl.java)、[会话锁 SQL](D:/canyun/houduan/sky-server/src/main/resources/mapper/AiChatSessionMapper.xml)。

### 15｜“你用什么向量数据库？相似度高就一定能回答？”

**正确的现状**：向量 JSON 存 MySQL，加载兼容的启用知识，Java 算余弦相似度、阈值过滤、全排序取 Top-K。不是专用向量数据库，也不是 ANN 或关键词混合检索。

**继续追问与要点**：

- **复杂度？** N 条候选、d 维向量，打分约 O(Nd)，M 条阈值通过结果排序 O(M log M)；当前把全部候选载入内存，不会因为 Top-K 小就只读取 K 条。
- **余弦是什么？** `dot(q,k)/(norm(q)*norm(k))`，衡量方向相似；不是答案正确率，也不是可直接解释的概率。
- **为什么校验模型与维度？** 不同模型可能是不同向量空间；维度相同也不代表语义坐标可比。模型更新后需要重新生成向量并切换版本。
- **无命中是否不调用模型？** 当前仍调用 Embedding；不调用的是聊天生成模型，两个阶段别混淆。
- **“不能退款”和“可以退款”都很相似怎么办？** 语义相关不代表规则一致。需要评测矛盾、否定、时效和适用条件，不能仅调高相似度阈值。
- **“那这张呢？”如何检索？** 当前只向量化本轮短句，虽然生成时带历史，检索阶段未做上下文改写，指代可能检索失败。
- **阈值怎么定？** 用标注的正例、近似负例、无答案问题评测，再权衡召回与拒答；未测不能声称准确率多少。

**改进顺序**：先建立评测集和知识版本记录；小库可继续精确扫描，大库根据测得的延迟/内存再考虑 ANN、混合检索、重排。不能只因加 AI 就默认需要复杂基础设施。

依据：[检索服务](D:/canyun/houduan/sky-server/src/main/java/com/sky/service/impl/AiKnowledgeRetrievalServiceImpl.java)、[候选查询](D:/canyun/houduan/sky-server/src/main/resources/mapper/AiKnowledgeMapper.xml)。

### 16｜“知识更新要调外部 Embedding，两个管理员一起改怎么办？”

**当前实现**：先在事务外生成新向量；短事务锁住旧知识版本，校验仍启用，停用旧版并插入版本号 +1 的新版。

**参考回答**：

> 预先查状态是为了少做无效的外部调用，不能保证后面状态不变。真正写入时通过 FOR UPDATE 和状态重检裁决。两个管理员同时编辑同一旧版本，后进入事务者发现旧版已停用后报冲突；停旧版与插新版同事务，新版插入失败会回滚旧版停用。

**边界**：失败一方可能已经付出了 Embedding 请求成本，数据库回滚无法退回外部调用。唯一 `(knowledge_key,version_no)` 约束版本不重复，但本身不等于数据库禁止所有绕过服务的写入创建多个启用版本。

**验证**：两个线程并发编辑同一版本、插入新版失败、生成向量失败、停用版本不参与检索。涉及真实供应商成本的验证应另行安排，不把 Mock 测试说成真调成功。

依据：[知识编排](D:/canyun/houduan/sky-server/src/main/java/com/sky/service/impl/AiKnowledgeServiceImpl.java)、[知识短事务](D:/canyun/houduan/sky-server/src/main/java/com/sky/service/impl/AiKnowledgePersistenceServiceImpl.java)。

### 17｜“用户传入的资料写着‘忽略规则’，JSON 转义能防注入吗？”

**参考回答**：

> JSON 序列化防止资料破坏格式，不会抹去资料的自然语言指令含义。系统提示能告诉模型把资料当数据，但不能给出绝对安全保证。应控制知识发布权限、版本审核、敏感数据最小化、工具白名单和服务端权限校验。当前没有 Tool Calling，不能把未来的工具权限控制说成已有。

**再问**：如何证明没有泄露订单？

当前模型没有订单查询工具，不等于以后加工具仍安全。接入后必须从 JWT 注入身份，按订单归属查，禁止模型指定任意 userId。建立跨用户查询、诱导泄密、资料注入、历史消息污染等测试；测试中“包含拒绝字符串”只能检查表面，不是完备的安全证明。

### 18｜“293 个测试都过了，为什么我还能找出这些问题？”

**参考回答**：

> 293 是 2026-08-30 三端历史测试计数，不是当前版本验证结果。测试通过说明已覆盖的输入与断言成立，不代表所有并发交错、崩溃窗口和业务路径都覆盖。Mock 不验证真实事务，少量并发重复也不构成严格证明。我应该同时用数据库约束和事务推理说明不变量，再用有控制的并发与故障注入测试检验关键窗口。

**面试官继续问**：

- 并发测试用屏障/锁存器控制交错，还是仅靠 sleep？
- 每个线程是否使用真实事务边界？测试方法上的事务会自动传到子线程吗？不会，应明确每个线程的事务和数据可见性。
- 新建对象直接调用方法与通过 Spring 代理调用，能验证同样的事务行为吗？不能。
- 用例验证的是模型请求格式、模拟检索结果，还是实际检索效果？
- 测试会连哪个数据库，是否与本地业务数据隔离，如何清理？

**验证优先级**：先定义不变量 → 写确定性交错测试 → 故障窗口注入 → 当前版本回归 → 再做压测。测试数和代码行数都不是能力证明的替代品。

## 三、三道必须能现场写的白板题

### 白板 A：算账

购物车：20 元 ×2、9 元 ×1；打包费每件 1 元；配送费 6 元；满 40 减 5。

期望：商品 49、打包 3、配送 6、原价 58、优惠 5、实付 53。门槛比较商品金额 49，不是原价 58。当前优惠额以总价为上限；到底能否抵配送费属于产品规则，不能自行换一种算法。

追问：前端把原价改为 0.01 怎么办？加入购物车之后菜品改价/停售怎么办？打包费改为 0.5 元后，当前 `intValueExact()` 对总打包费非整数的情况会怎样？

### 白板 B：写 SQL，删条件看后果

```sql
-- 领取模板库存；实际还需状态与领取时间条件
UPDATE coupon SET stock=stock-1
WHERE id=? AND stock>0 AND status=1;

-- 下单锁券；实际还需有效期与商品门槛条件
UPDATE user_coupon SET status=1, order_id=?
WHERE id=? AND user_id=? AND status=0;

-- 释放必须匹配旧订单，防止旧请求释放新绑定
UPDATE user_coupon
SET status=CASE WHEN valid_end_time>? THEN 0 ELSE 3 END,
    order_id=NULL, locked_time=NULL
WHERE id=? AND order_id=? AND status=1;
```

追问：分别去掉 stock、user_id、order_id、status 条件会有什么反例？影响行数 0 是系统异常、竞争失败还是幂等成功？应按具体业务语义判断，不能全都重试。

### 白板 C：联合索引不是背一个答案

历史订单可能有两种查询：`user_id + order_time 排序`，以及 `user_id + status + order_time 排序`。`(user_id,status,order_time)` 对后一种有用，但 status 不参与过滤时，不能笼统承诺它天然满足全体订单按时间排序。

应结合查询比例考虑 `(user_id,order_time,id)` 与带 status 的索引，用 EXPLAIN、实际数据量和写入成本取舍。基础建表脚本并不完整，不要把“建议建索引”写成“数据库一定已经有索引”。

再问：`UNIQUE(order_id)` 为什么允许多张未使用券？MySQL 唯一索引允许多个 NULL；同一非 NULL 订单号则不能重复。它约束的是同一订单不能在多条用户券记录中出现，不单独解决历史订单是否重复引用同一张券。

## 四、不能无边界承诺的十句话

| 容易翻车的说法 | 更严谨的说法 |
| --- | --- |
| 加事务所以不重复下单 | 事务保原子性，建单幂等需独立协议 |
| 最先收到支付请求的一方获胜 | 最终由条件更新和事务提交结果裁决 |
| 15 分钟绝对关单 | 当前每分钟扫描，严格截止校验尚未闭环 |
| 支付接口成功就是到账 | 当前只是演示支付 |
| REQUIRES_NEW 当前一定挂起外层事务 | 当前调度路径原取消事务已结束，其他入口才可能挂起 |
| 抢占保证任务只执行一次 | 宕机和租约回收可能重复，业务仍须幂等 |
| processing_time 防住所有旧执行者 | 当前只保护任务回写，不保护任意外部副作用 |
| SUCCESS 表示所有订单券数据已对账 | 当前主要表示业务调用正常返回 |
| 使用 RAG 就不会幻觉 | 检索相关性、证据充分性和生成正确性要分别评测 |
| 测试通过代表生产可靠 | 仅证明当前运行所覆盖的断言成立 |

## 五、怎么练，才不是背答案

每轮只练一组，先不看参考回答。

1. 用 60～90 秒口述当前实现。
2. 面试官挑一个条件反问“删掉会怎样”。
3. 用两线程/失败时间线解释，不能只说“会有并发问题”。
4. 打开具体方法和 SQL 验证，记下与口述不一致之处。
5. 给出一个最小改进和一条可执行测试，再回答一次。

建议训练顺序：01 → 02 → 04 → 08 → 09 → 10 → 03 → 05～07 → 11～12 → 13～18。

一次能答完不代表掌握；第二天换一种问法，仍能从数据状态推导出答案，才算吃透。你可以不做所有扩展，但必须知道当前保证到哪里、哪里还没做，以及为什么。
