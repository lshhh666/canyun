# Java 后端简历写作与 STAR 应用

整理日期：2026-09-13。默认用于 Java 后端实习/校招；尚未提供个人学历、经历和目标岗位 JD，相关内容保留待填写。

## 1. 查阅资料得到的写作依据

- 哈佛职业中心强调针对目标职位、用具体行动和事实呈现成果，避免空泛和华丽措辞。对餐云的应用：把“熟悉事务”落实到订单与优惠券共同提交、失败回滚的具体设计。[哈佛简历指南](https://careerservices.fas.harvard.edu/resources/create-a-strong-resume/)
- 伯克利建议学生使用简洁的一页简历，包含联系方式、教育背景和技能，按实际经历加入项目/工作经历；网申使用常规标题与清晰格式，并遵循上传格式要求。[伯克利简历指南](https://www.career.berkeley.edu/prepare-for-success/resumes/)
- 华盛顿大学将 STAR 用于行为面试：Situation 背景、Task 任务、Action 个人行动、Result 结果，强调讲清个人贡献。[STAR 方法](https://careers.uw.edu/resources/star-method-of-interviewing/)

这些是写作依据，具体栏目顺序和餐云亮点取舍是结合 Java 后端岗位作出的建议；海外指南中的个人信息习惯不机械等同于所有国内招聘要求。

## 2. 一份完整简历放哪些部分

| 部分 | 要写的内容 | 餐云求职者的安排 |
| --- | --- | --- |
| 基本信息与求职意向 | 姓名、电话、邮箱、Java 后端方向；可访问的作品链接 | 实习可补到岗时间、每周出勤和持续时长，均按事实填写 |
| 教育背景 | 学校、专业、学历、起止时间/预计毕业时间 | 成绩、排名、相关课程有帮助再写，排名应带分母 |
| 专业技能 | 与职位相关、能够解释并实践的知识 | 建议 4～6 条，每条一个能力领域，不直接照抄项目依赖清单 |
| 实习/工作经历 | 真实单位、岗位、时间、个人行动与结果 | 有相关经历可优先于项目；没有就删掉栏目 |
| 项目经历 | 项目名、时间、角色、简介、核心技术、3～5 条贡献 | 餐云作为一个完整项目，交易和 AI 是其中两条主线 |
| 荣誉与其他能力 | 有含金量的比赛、奖学金、英语、开源贡献 | 精选 2～3 项；普通自我评价和无关爱好不必占位 |

没有实习时，推荐“基本信息 → 教育 → 技能 → 项目 → 荣誉”。有较强相关实习时，将其放在项目之前。不是每个栏目都必须凑齐。

## 3. STAR 怎么用在这个项目上

STAR 用来梳理材料；简历中无需逐项打印 S/T/A/R。推荐压缩为：

> 针对【具体问题】，通过【本人实现的关键措施】，实现【可解释的结果】，并以【验证证据】支撑。

不要求每条都包含四个分句。项目简介交代背景，贡献条目突出行动和结果即可。面试追问时再补完整故事。

### 示例 A：优惠券并发领取

| STAR | 餐云中的内容 |
| --- | --- |
| S：背景 | 同一优惠券允许多个用户领取，同一用户也可能重复提交 |
| T：任务 | 防止库存扣成负数，且同一用户不能重复领取同一模板 |
| A：行动 | 使用带库存/状态/时间条件的 UPDATE 扣库存，以用户与模板联合唯一索引防重，并将扣库存和用户券插入放入同一事务 |
| R：结果 | 竞争失败时不产生重复用户券，插入失败会回滚库存；通过真实数据库相关用例检验这一设计，运行结果以对应报告为准 |

简历句：

> 针对优惠券并发领取，采用库存条件更新与用户—券模板联合唯一索引，并将扣库存和用户券创建纳入同一事务，处理库存超扣及重复领取时的数据一致性问题。

### 示例 B：客服问题怎样真正处理完

| STAR | 餐云中的内容 |
| --- | --- |
| S：背景 | 用户评价“没解决”后，需要追踪知识修正是否有效 |
| T：任务 | 将问题关联到知识，并以可查看、可确认的复测结果决定是否关闭 |
| A：行动 | 建立反馈、知识关联、复测与人工确认流程；反馈行锁串行化同一反馈的提交；复测记录实际使用的版本；确认结果与反馈关闭同事务提交 |
| R：结果 | 已记录真实页面成功、确认错误、重新复测和最终关闭验收；真实 MySQL 并发提交验证只创建一条活动复测任务 |

简历句：

> 建立用户负反馈、知识修正、后台复测与人工确认闭环，复测成功且人工确认正确后关闭反馈；通过反馈行锁控制重复提交，真实 MySQL 并发测试验证两个管理员同时操作只创建一条复测任务。

这一结果依据已有验收记录，不等于本次重新跑过验收，也不能推导回答准确率提升。

## 4. 没有业务规模，结果如何写

结果可以是可验证的行为：并发只有一条记录、失败整体回滚、旧执行结果被拒绝、用户能完成闭环。它不一定是百分比。

- “配置 1/5/15 分钟重试”描述方案参数，不是性能成果。
- “两个管理员并发只创建一条任务”描述验证场景，不是系统并发容量。
- “拥有多种状态”是建模细节，不如说明哪些非法状态组合被阻止。
- 测试数量仅在同一轮、明确范围、去重且能查报告时使用；各轮局部报告不能累加成最新全量通过数。

如果以后确实采集性能或效果数据，应同时记录环境、数据量、输入集、测量方式和前后口径。当前写简历不必为了凑数字额外造指标。

## 5. 技能栏目如何与项目互相印证

以下是可供本人核对的写作候选，不能由“仓库中存在代码”推断本人已掌握：

- Java：能够使用集合、异常处理、BigDecimal 和面向对象设计实现业务逻辑。
- Spring Boot / Spring MVC / MyBatis：能够实现分层接口与数据访问；理解 Spring 声明式事务、传播行为和代理调用边界。
- MySQL：理解索引、唯一约束、行锁和事务，能够用条件更新处理库存与业务状态竞争。
- Redis：能够在菜单查询中使用缓存、过期和更新失效策略，并解释数据不一致窗口。
- AI 应用：能够实现 Embedding 检索、RAG、受控业务查询、会话状态控制与异步任务恢复。
- 工程实践：能够编写 JUnit/Mockito 测试，使用 Maven、Git，完成接口联调和问题定位。

Java 并发、JVM、网络、Linux 等若确实掌握且岗位要求可补充。项目中有并发测试不代表已经证明候选人精通 JUC；不熟练的内容不写“精通”。

## 6. 排版与投递检查

建议先做一页、单栏、可复制文字的版本，常规栏目标题，正文保持正常可读字号。导出后检查断行、链接、日期、标点和复制顺序；上传 PDF 或 Word 按招聘系统要求处理。[网申格式依据](https://www.career.berkeley.edu/prepare-for-success/resumes/)

以下是针对本项目的筛选检查：

1. 看一眼能否知道你投 Java 后端，以及何时毕业/到岗？
2. 每个“设计/实现/重构”是否对应本人的实际工作？
3. 项目是否同时展示交易一致性和 AI 应用特色，避免几条都在重复讲任务重试？
4. 技术方案是否对应明确问题，结果是否有证据？
5. 每条能否解释一次正常流程、一次并发或失败流程？
6. 是否保留个人项目性质和真实时间，未写虚构公司、线上用户或性能收益？

餐云的支付采用演示流程是项目范围约定，可在项目说明中简短注明；不需要写成一条“尚未完成”的个人不足。项目代码分析与推荐条目见 [项目分析](D:/canyun/docs/cloudmeal-project-resume-analysis.md) 和 [简历项目段](D:/canyun/docs/cloudmeal-resume-project-highlights.md)。
