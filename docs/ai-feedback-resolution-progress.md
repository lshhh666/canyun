## 已完成

- `ai_chat_feedback` 已增加处理状态、处理管理员和处理时间。
- 已建立反馈与知识的多对多关系表，关系使用稳定的 `knowledge_key`。
- 已建立知识向量任务表和反馈复测记录表。
- 知识新增：同一事务保存 `PENDING` 知识与向量任务。
- 知识修改：锁定旧版本，停用旧版本、作废旧任务、创建新版本及新任务。
- RAG 只检索 `ENABLED + READY` 的知识，生成中的知识不参与检索。
- 向量任务先短事务抢占，再在事务外调用模型。
- 任务支持首次执行失败后最多自动重试 3 次，间隔为 1、5、15 分钟。
- 处理超过 2 分钟的任务会恢复为待执行。
- 使用 `processing_time` 作为本轮抢占令牌，迟到的模型结果不能覆盖新任务状态。
- 旧版本在模型运行期间被停用时，任务会标记为 `OBSOLETE`。
- 最终失败后知识标记为 `FAILED`，不会参与 RAG。
- 已为抢占参数增加空值安全比较。
- 已完成当前有效知识分页接口，支持关键词、分类和向量状态筛选。
- 分页接口不返回向量 JSON，只返回管理页面需要的字段。
- 知识新增、修改接口会返回知识 ID、`PENDING` 状态和“保存成功，向量同步中”。
- 已完成独立“知识管理”页面，可新建、修改、筛选并刷新向量状态。
- 页面明确区分“同步中、可用、同步失败”，并防止旧分页响应覆盖新结果。
- 最终失败知识支持人工重新同步，复用原任务并开启新一轮最多3次的自动重试。
- 人工重试接口具有幂等性：同步中不重复排队，已经可用不重复执行。
- 知识任务与知识记录的事务统一按“任务行→知识行”加锁，避免反向加锁导致死锁。
- 管理端只对 `FAILED` 记录显示“重新同步”，提交后刷新为“同步中”。
- 管理端“没解决”列表已展示处理状态，并支持进入“关联知识并发起复测”。
- 复测问题默认取评价对应的最后一个用户问题，管理员可在提交前修正。
- 知识选择支持按标题或稳定 `knowledge_key` 远程搜索，只展示 `READY` 知识。
- 发起复测时，管理员 ID 只从 ThreadLocal 获取，不接收前端身份字段。
- 后端要求所有所选知识都是当前启用、已同步且与当前向量模型和维度一致；前端筛选不能替代后端校验。
- 同一短事务内替换反馈知识关联、创建 `PENDING` 复测记录，并把反馈推进为 `PENDING_RETEST`。
- 同一反馈的并发提交统一先锁反馈行，再检查活动复测；已有待执行、执行中或待人工确认任务时直接幂等返回。
- 后台定时小批量扫描到期复测，条件更新抢占成功后立即提交短事务，再在事务外调用模型。
- 复测只使用该反馈关联的当前 `ENABLED + READY` 知识，不执行取消订单等业务工具，也不写入用户会话。
- 线上 RAG 与后台复测共用同一个受知识约束的回答生成器，避免两套提示词和生成规则逐渐不一致。
- 复测成功会保存回答和实际使用的知识版本 ID 快照；失败按 1、5、15 分钟自动退避重试。
- 处理超过2分钟的复测会恢复为待执行，旧执行器必须携带原 `processing_time` 才能写结果，因此迟到结果不会覆盖新执行。
- 首次执行加3次自动重试仍失败才进入 `FAILED`；内部错误只留在后台，不返回用户端。
- 管理端可查看反馈最新一次复测的问题、回答、执行状态、重试次数、知识版本快照和内部错误摘要。
- `PENDING/PROCESSING` 复测详情每5秒低频刷新，完成或失败后自动停止轮询，页面销毁时也会释放定时器。
- 只有 `SUCCEEDED` 且尚未人工确认的复测允许提交确认；管理员ID仍只从 ThreadLocal 获取。
- 确认“回答正确”时，复测确认和反馈标记 `HANDLED` 在同一事务完成；任何一步失败都会回滚。
- 确认“回答仍不正确”不会关闭反馈，管理员可修改知识并重新发起复测。
- 重复或冲突确认幂等返回第一次结果，不能由后一次请求改判，防止重复点击和并发操作。
