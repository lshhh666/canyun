## 0. 先记住这条主线

这个项目真正值得讲的不是“做了一个外卖系统”，而是：

> 我在基础点餐业务上，把订单金额改为服务端权威计价，并补全了优惠券从创建、领取、锁定、核销到释放的全链路；针对重复领取、库存超扣、支付与取消并发等问题，用唯一索引、带状态条件的原子更新和本地事务保证一致性；对于数据库异常导致超时取消长期失败的情况，又设计了独立补偿任务，通过 `REQUIRES_NEW`、任务抢占、有限重试、超时回收和人工兜底实现最终恢复。

面试时围绕这条线展开，普通 CRUD 只作为业务背景。

## 3. 项目介绍话术

### 3.1 30 秒版本

> 餐云是一个餐饮外卖点餐项目，包括 Java 后端、Vue 管理端和微信小程序。基础功能有菜品、套餐、购物车、订单和经营报表。我主要深入做的是服务端订单计价和优惠券一致性：领取时用唯一索引和原子扣库存防重复与超卖，下单先锁券，支付后核销，取消或超时释放；支付和取消并发时由带状态条件的订单更新决定唯一胜者，并用同一事务保证订单和券一起成功或回滚。对于长期失败，我又做了独立补偿任务和有限重试。

### 3.2 1 分钟版本

> 项目采用 Spring Boot + MyBatis + MySQL + Redis，前端是 Vue 管理端和 UniApp 小程序。用户从微信登录后浏览菜品、加入购物车、选择地址和优惠券，后端重新计算菜品金额、打包费、配送费，并通过百度地图校验 5 公里配送范围，然后创建订单和金额快照。
>
> 这个项目最难的是优惠券和订单的一致性。优惠券领取不能只“先查库存再扣减”，因为并发下会超卖，所以库存扣减是一条带状态、时间和 `stock > 0` 条件的 SQL；同一用户重复领取再由 `(user_id, coupon_id)` 唯一索引兜底。下单时券从 AVAILABLE 原子更新为 LOCKED 并绑定订单，支付转 USED，取消转 AVAILABLE 或 EXPIRED。支付和取消都先条件更新订单，再更新券，并处于同一事务，最终只能出现支付成功或取消成功两种一致状态。超时取消若持续失败，会用新事务记录补偿任务，按间隔重试并最终转人工。

### 3.3 3 分钟版本的结构

不要从员工 CRUD 开始念。按以下顺序讲：

1. **业务**：管理端管理商品和订单，小程序完成点餐、领券和支付。
2. **架构**：Nginx → Spring MVC → Service → MyBatis → MySQL/Redis；WebSocket 推送提醒；第三方接微信、地图和 OSS。
3. **你的重点**：权威计价、优惠券状态机、并发一致性、失败补偿。
4. **测试**：单元测试 + 真实数据库集成测试 + 并发测试 + 三端契约测试。
5. **边界**：支付是演示版；AI 已有基础后端 RAG，前端会话串联与工具调用仍待完成；说清下一步怎么演进。

## 4. 架构和请求链路

```text
微信小程序 ── /user/** ─────────────┐
                                      │
Vue 管理端 ── /api/** ── Nginx ──> /admin/** ──> Spring MVC
                                                        │
                  JWT 拦截器 → Controller → Service → Mapper
                                                        │
                                               MySQL / Redis
                                                        │
                             微信接口 / 百度地图 / 阿里云 OSS / 智谱 AI

Spring WebSocket /ws/{sid} ──> 管理端新订单与催单通知
Spring Scheduling ──> 超时订单扫描、补偿扫描、派送订单自动完成
```

### 4.1 Maven 多模块

- `sky-common`：通用结果、异常、配置属性、上下文、工具类。
- `sky-pojo`：DTO、Entity、VO、枚举。
- `sky-server`：Controller、Service、Mapper、定时任务、WebSocket。

**为什么拆模块？**

> 将通用能力、数据模型和业务服务分离，减少循环依赖并方便复用。当前仍是单体部署，不是微服务；Maven 多模块只代表代码组织和构建边界。

### 4.2 DTO、Entity、VO 为什么分开

- DTO 接收客户端允许提交的字段。
- Entity 对应数据库持久化对象。
- VO 是面向页面的返回模型。
- 防止直接暴露数据库字段，也避免客户端提交服务端拥有的状态和金额。

本项目下单时曾有一个典型问题：如果直接 `BeanUtils.copyProperties`，客户端字段可能覆盖服务端报价，包装类型复制到基本类型还可能触发拆箱空指针。因此当前只逐项复制地址、支付方式、备注等用户可选字段，金额、状态和时间由服务端设置。

## 5. 从登录到完成订单，完整吃透

### 5.1 微信登录

1. 小程序调用 `uni.login` 获取临时 code。
2. 后端使用 AppID、secret、code 请求微信 `jscode2session`。
3. 得到 openid；用户不存在就落库。
4. JWT 中只写服务端查询出的 userId。
5. 用户后续请求把 token 放在 `authentication` 请求头。
6. 用户拦截器验签并将 userId 写入 `ThreadLocal`。

**为什么不能让前端传 userId？**

因为用户可以篡改参数。如果查询订单接口只按前端 userId 查询，就会形成水平越权。项目所有“我的订单、我的券、地址、催单、再来一单”都应以 JWT 上下文为身份来源，并继续校验资源归属。

### 5.2 浏览菜单和缓存

- 菜品按分类缓存为 `dish_category_{categoryId}`，TTL 30 分钟。
- 套餐使用 Spring Cache，缓存名为 `setmealCache`。
- 管理端增删改、起售停售后删除对应缓存，采用 Cache Aside 思路。

当前策略是“先写数据库，再删缓存”的变体，但部分事务边界放在 Controller，缓存删除发生在事务提交前，严格来说仍可能出现数据库回滚但缓存已经删除，或者并发读把旧值重新写回的问题。单体低并发场景可接受；生产改造见场景题。

### 5.3 购物车

- 加菜时根据服务端菜品/套餐信息写入名称、图片和单价快照，前端不直接提交单价。
- 同一用户同一菜品再次添加则数量加一。
- 下单成功后在事务内清空购物车。

**当前隐患**：购物车单价是加入时的快照。若菜品后来改价或停售，下单计价没有再次查询当前商品状态与价格。更严格的实现应在预览/提交时批量查询当前商品，校验有效性并重新计价，或者明确规定“购物车价格只短期锁定”并设置过期时间。

### 5.4 服务端权威计价

`OrderPricingServiceImpl.preview` 的步骤：

1. 按当前 userId 查购物车，空购物车拒绝。
2. 按 addressBookId 查地址并校验地址属于当前用户。
3. 调百度地图地理编码和路线规划，超过配置的 5000 米拒绝。
4. 使用 `BigDecimal` 累加 `单价 × 数量` 得到菜品金额。
5. 打包费 = 每件打包费 × 商品件数。
6. 加固定配送费，生成预计送达时间。
7. 下单时再次调用相同计价服务，不能只相信预览结果，更不能相信前端 amount。

**为什么预览后提交还要重算？**

预览和提交之间购物车、价格、地址或活动可能变化，前端预览结果也可被篡改。真正落库前必须重新校验和计价。

### 5.5 下单事务

事务内完成：

1. 重算服务端报价。
2. 初步校验用户券归属、状态、有效期和门槛。
3. 插入订单，保存原价、优惠额、实付额、用户券 ID 快照。
4. 用条件更新把券从 AVAILABLE 改为 LOCKED，并绑定刚生成的 orderId。
5. 插入订单明细。
6. 清空购物车。

任何一步抛异常，订单、券、明细和购物车变更全部回滚。

**为什么要先插订单再锁券？**

锁券需要绑定真实 orderId，而 orderId 是数据库自增生成的。二者在同一事务中，即使先插订单，只要锁券失败，订单也会回滚，不会留下脏订单。

### 5.6 支付

当前是演示支付：客户端调用后端接口，后端直接把待付款订单条件更新为已支付待接单，然后核销优惠券并通过 WebSocket 通知管理端。

支付 SQL 的关键条件是：

```sql
UPDATE orders
SET status = 2, pay_status = 1, ...
WHERE id = ?
  AND user_id = ?
  AND status = 1
  AND pay_status = 0;
```

影响行数为 1 才说明本线程赢得状态转换。若券核销失败，支付事务回滚。

重复调用已确认支付的订单会直接返回，体现基础幂等性。但真实支付必须以支付平台回调为准。

### 5.7 主动取消和超时取消

- 用户主动取消：校验订单属于当前用户，只允许待付款未支付订单取消。
- 超时取消：定时任务每分钟查询下单超过 15 分钟且未付款的订单。
- 两者都执行 `WHERE status=1 AND pay_status=0` 的条件更新。
- 取消成功后，券仍有效则恢复 AVAILABLE，已过期则转 EXPIRED。
- 券释放必须同时匹配 `user_coupon_id + order_id + LOCKED`；失败则取消事务回滚。

## 6. 优惠券状态机：本项目第一核心

### 6.1 为什么有 coupon 和 user_coupon 两张表

`coupon` 是活动模板，记录发行库存、门槛、优惠额和领取/使用时间。
`user_coupon` 是用户领到的具体资产，保存领取时快照。

如果只保留模板 ID，运营以后修改模板，历史用户券的金额和有效期也会被改变。快照隔离了历史规则，是典型的“交易数据不可被配置变化追溯修改”。

### 6.2 模板状态机

```text
DRAFT(草稿) ──开始发放──> DISTRIBUTING(发放中) ──停止──> DISABLED(停用)
```

- 只有草稿能编辑、删除和开始发放。
- 只有发放中能停止。
- 状态转换不仅在 Java 里校验，还在 SQL 的 WHERE 中校验。

Java 前置校验用于友好提示；SQL 条件更新才是并发下的最终裁决。

### 6.3 用户券状态机

```text
AVAILABLE ──下单──> LOCKED ──支付──> USED
    │                   │
    └──到期──> EXPIRED  └──取消──> AVAILABLE / EXPIRED
```

### 6.4 为什么下单时锁券而不是核销

- 直接核销：用户不付款会损失优惠券。
- 完全不锁：同一张券能绑定多个待付款订单。
- 所以先 LOCKED，支付才 USED，取消则释放。

### 6.5 并发领取为什么安全

分两类问题：

**库存超扣**：

```sql
UPDATE coupon
SET stock = stock - 1
WHERE id = ?
  AND stock > 0
  AND status = 1
  AND receive_start_time <= ?
  AND receive_end_time >= ?;
```

InnoDB 对同一行更新会串行化；库存为 0 后条件不成立，不会扣成负数。

**同一用户重复领取**：

- 前置查询用于快速给出“已领取”提示。
- `(user_id, coupon_id)` 唯一索引做最终防重。
- 两个请求都通过前置查询时，只能有一个插入成功。
- 失败请求抛异常，事务把它之前的库存扣减一起回滚。

这叫“业务校验 + 数据库约束兜底”，不能只依赖先查后插。

### 6.6 为什么不用 Redis 分布式锁

推荐回答：

> 当前库存和用户券都在同一个 MySQL 库，单条条件更新和唯一索引就能在数据源处完成正确性约束，链路短、失败模型简单。Redis 锁还要处理过期、续期、误删和 Redis/数据库双写一致性，不能替代数据库约束。若未来是秒杀级流量，我会在入口增加 Redis 库存预扣、Lua 原子校验和 MQ 削峰，但 MySQL 唯一索引仍保留作为最终防线。

### 6.7 这是乐观锁吗

可以说是“基于状态条件的 CAS/乐观并发控制”，但不是 MyBatis-Plus `version` 字段式乐观锁。

> 更新时假设状态没有变化，把旧状态写进 WHERE；影响行数为 1 表示成功，0 表示状态已被其他事务改变。业务状态本身就承担了版本条件。

## 7. 支付与取消竞争：本项目第二核心

### 7.1 错误写法

```java
Orders order = selectById(id);
if (order.getStatus() == PENDING_PAYMENT) {
    updateToPaidOrCancelled(id);
}
```

两个线程可能同时读到待付款，然后一个支付、一个取消，产生“已取消但 pay_status=已支付”或优惠券混合状态。

### 7.2 当前正确做法

支付和取消都把“旧状态”放入 UPDATE 条件，并更新同一订单行：

- 支付：`status=1 AND pay_status=0 → status=2 AND pay_status=1`
- 取消：`status=1 AND pay_status=0 → status=6 AND pay_status=0`

InnoDB 会对订单行加排他锁。第一个事务修改并提交后，第二个事务重新判断 WHERE，条件不再成立，影响行数为 0。

### 7.3 为什么还需要事务

条件更新只决定谁赢，事务保证赢的一方内部一致：

- 支付赢：订单支付和券核销同时提交。
- 取消赢：订单取消和券释放同时提交。
- 券更新失败：订单更新一起回滚。

### 7.4 为什么统一“先订单、后优惠券”

多个事务以不同顺序锁资源容易死锁。例如支付先锁订单再锁券，而取消先锁券再锁订单，就可能循环等待。统一访问顺序能显著降低死锁概率。

仍不能说“绝对不会死锁”。生产系统还应捕获死锁错误并对幂等操作做有限重试。

### 7.5 最终合法状态

| 竞争结果 | 订单 | 支付状态 | 用户券 |
| --- | --- | --- | --- |
| 支付胜出 | 待接单 | 已支付 | USED |
| 取消胜出 | 已取消 | 未支付 | AVAILABLE 或 EXPIRED |

其他组合都应视为异常。

## 8. 失败补偿：本项目第三核心

### 8.1 本地事务为什么还不够

假设超时取消已更新订单，但释放优惠券时发现绑定数据异常：事务可以回滚，避免“订单取消、券仍锁定”的混合状态；但回滚后订单仍然待付款，故障不会自动消失。

事务解决原子性，补偿机制解决长期恢复。

### 8.2 为什么用 REQUIRES_NEW

失败记录必须独立提交。如果它加入原取消事务，取消事务回滚时补偿记录也会消失，系统甚至不知道有异常。

`REQUIRES_NEW` 在存在活动外层事务时会挂起它并开启新事务；当前 OrderTask 是在取消调用抛错、其事务结束后记录失败，这条路径其实没有活动外层事务要挂起。它仍明确保证其他带事务调用入口下的独立提交语义。项目另有测试验证：人为开启外层事务并回滚后，补偿记录仍存在。

### 8.3 补偿状态机

```text
PENDING ──原子抢占──> PROCESSING ──成功──> SUCCESS
   ^                       │
   │                       ├──失败未达上限──> PENDING（5分钟后）
   │                       └──第3次失败──> MANUAL
   └──── PROCESSING 超过10分钟回收 ────────┘
```

### 8.4 多实例如何竞争处理权

实例先查询候选任务，再执行：

```sql
UPDATE order_compensation_task
SET status = PROCESSING, processing_time = ?
WHERE id = ? AND status = PENDING AND next_retry_time <= ?;
```

只有影响行数为 1 的实例获得本次处理权。查询可以重复，处理权由条件更新决定。但业务提交后、任务标记成功前宕机，或超时回收时旧执行者尚未停止，仍可能重复进入业务；这不是 exactly-once，仍需业务幂等。

### 8.5 processing_time 为什么既是时间又是持有权标识

成功和失败更新都要求 `status=PROCESSING AND processing_time=本次值`。新实例接管且标识改变后，旧实例不能覆盖新实例的任务记录。这只是任务回写的持有权检查，不是完整业务 fencing：旧实例仍可能继续调用业务方法，必须靠订单条件更新与幂等防止错误副作用。更严格可增加 claim_version/claim_token，并让实际执行副作用的资源校验持有权；时间戳还受精度和跨节点时钟偏差影响。

### 8.6 为什么不是无限重试

- 瞬时故障需要间隔后重试。
- 永久脏数据不会因为高频重试自动恢复。
- 无限重试会制造数据库压力和日志噪声。
- 所以 5 分钟间隔、最多 3 次，之后转人工。

### 8.7 为什么补偿重做完整取消，而不是只释放券

补偿开始时订单可能已经支付或被其他流程处理。重做完整业务流程可以重新检查订单状态并保持幂等；单独释放券可能把已支付订单的券错误释放。

### 8.8 与 MQ 的关系

当前方案是业务失败后独立写数据库任务表，不是业务成功与事件同事务提交的 Outbox；不要混为一谈。它适合单库单体、量不大的场景。规模增大后可按具体事件设计：

1. 业务事务内写 Outbox 事件。
2. 可靠发布到 MQ。
3. 消费者幂等处理取消/核销。
4. 任务表或死信队列继续承担失败追踪和人工处理。

MQ 不是自动一致；仍要处理消息至少一次、重复消费、乱序和最终失败。

## 9. 认证、权限和安全

### 9.1 JWT 结构和校验

JWT 一般是 `header.payload.signature`：

- header：算法和令牌类型。
- payload：声明，本项目写 employeeId 或 userId。
- signature：服务端使用 HS256 密钥签名，防止内容被篡改。

JWT 默认只编码不加密，不能把密码、手机号等敏感信息放进 payload。

### 9.2 管理端和用户端为什么分密钥

项目有两套 header 名和密钥：管理端 token、用户端 authentication。分开可缩小密钥泄漏影响范围，并防止把用户令牌误当管理员令牌使用。正式部署必须提供稳定高强度环境变量；开发环境随机密钥会使重启后旧 token 失效。

### 9.3 ThreadLocal 的作用和当前问题

作用：同一请求线程内，拦截器写入 userId，后续 Service/Mapper 无需层层传参就能获取当前身份。

原理：每个线程维护自己的 ThreadLocalMap，线程之间数据隔离。

当前代码定义了 `removeCurrentId()`，但拦截器没有在 `afterCompletion` 调用。Servlet 线程池会复用线程，可能造成引用残留，甚至在某些错误路径中读到旧身份。

正确改造：

```java
@Override
public void afterCompletion(HttpServletRequest request,
                            HttpServletResponse response,
                            Object handler, Exception ex) {
    BaseContext.removeCurrentId();
}
```

更稳妥也可用 Filter 的 `try/finally` 清理。

### 9.4 水平越权怎么防

- 当前用户 ID 只来自 JWT 上下文。
- 查询订单后比较 `order.userId` 与当前 userId。
- “不存在”和“不属于当前用户”统一返回订单不存在，减少订单 ID 枚举信息泄漏。
- 再来一单、催单、详情、取消都必须校验，不只在列表接口校验。

### 9.5 当前密码安全问题

员工密码使用普通 MD5。MD5 速度快且没有盐，抵抗彩虹表和暴力破解能力弱。生产应改为 BCrypt/Argon2，每个密码自动随机盐，并设计旧密码渐进迁移。

### 9.6 图片上传为什么不能只看后缀和 Content-Type

Content-Type 和文件名都由客户端提供，可以伪造。当前实现：

- 限制 2MB。
- 只接受 PNG/JPEG/WebP MIME。
- 使用 ImageIO 识别真实格式并完整解码。
- 比较真实格式与 MIME。
- 限制最大边长和总像素，降低图片炸弹风险。
- 服务端生成 UUID 对象名，目录只允许受控字符。

进一步可增加病毒扫描、图片重编码、OSS 私有读、签名 URL 和内容安全审核。

## 10. Redis、缓存和 WebSocket

### 10.1 Redis 在本项目做什么

- 门店营业状态。
- 菜品分类缓存。
- Spring Cache 套餐缓存。

没有把 Redis 用作订单最终状态或优惠券最终库存，核心交易仍以 MySQL 为准。

### 10.2 缓存穿透、击穿、雪崩怎么结合项目答

**穿透**：大量查询不存在分类。可缓存空列表并设置短 TTL，入口做参数校验，必要时布隆过滤器。当前菜品代码只在非空缓存命中时返回，空列表不会有效防穿透。

**击穿**：热门分类缓存过期，大量请求同时查库。可使用互斥锁、逻辑过期异步刷新或随机预热。

**雪崩**：大量 key 同时过期或 Redis 故障。可给 TTL 加随机值、多级缓存、限流熔断和 Redis 高可用。

### 10.3 数据库和缓存不一致怎么改

基础方案：更新数据库成功后删除缓存。更严格方案：

- 缓存删除放到事务提交后执行，避免数据库回滚但缓存先删。
- 延迟双删可降低旧值回填概率，但不天然构成强一致证明；订阅 binlog 也需可靠消费、重试和处理失效/回填竞争。
- 热点数据设置版本号，防旧值覆盖新值。
- 明确 Redis 故障时回源、限流和降级策略。

### 10.4 WebSocket 在项目中的作用

支付成功后向管理端推新订单，用户催单时推催单消息；相比轮询能降低无效请求并缩短通知延迟。

当前实现使用静态内存 `HashMap<sid, Session>` 并向所有连接群发，存在并发访问风险；改用 ConcurrentHashMap 是建议，不是已经实现。还需处理同一 Session 的并发发送、重复 sid 和旧连接关闭误删新连接的问题。多实例部署需要 Redis Pub/Sub、MQ 或独立 WebSocket 网关进行跨节点通知，并补充连接鉴权、心跳、断线重连、定向推送和背压控制。

### 10.5 WebSocket 和 HTTP 区别

- HTTP 通常是一问一答；WebSocket 建立后是全双工长连接。
- WebSocket 初始握手仍通过 HTTP Upgrade。
- Nginx 必须转发 `Upgrade` 和 `Connection` 头；项目配置已经处理。

## 11. Spring、MyBatis、MySQL 项目八股

### 11.1 Spring IOC 是什么，本项目怎么体现

IOC 把对象创建、依赖装配和生命周期交给 Spring 容器。Controller、Service、Mapper 配置、拦截器和任务都是 Bean，通过依赖注入协作。

当前很多代码使用字段注入；新代码更推荐构造器注入，因为依赖不可变、便于单元测试，也能更早暴露循环依赖。

### 11.2 AOP 是什么，本项目怎么体现

AOP 把事务、日志、鉴权、审计等横切逻辑从业务代码中抽离。本项目：

- `@Transactional` 通过代理织入事务。
- `AutoFillAspect` 拦截带 `@AutoFill` 的 Mapper 方法，用反射填充创建/更新时间和操作人。

### 11.3 @Transactional 为什么可能失效

常见原因：

- 同类内部 `this.method()` 自调用绕过代理。
- 方法不是可代理的 public 方法。
- 异常被吞掉，没有抛出代理边界。
- 抛出 checked exception 但没配置 `rollbackFor`。
- 对象不是 Spring Bean。
- 数据库表不是事务引擎。

本项目 `OrderTask → OrderService`、`OrderTask → OrderCompensationService` 都是跨 Bean 调用，能经过代理；核心方法显式 `rollbackFor = Exception.class`。

### 11.4 REQUIRED 和 REQUIRES_NEW 区别

- REQUIRED：有事务就加入，没有就新建。订单、订单明细、锁券和清购物车需要同一事务。
- REQUIRES_NEW：挂起当前事务，独立新建。补偿失败记录必须在外层回滚时仍提交。

### 11.5 MyBatis 和 MyBatis-Plus 为什么混用

MyBatis-Plus 适合标准单表 CRUD 和 Lambda 条件；复杂联表、动态 SQL、条件状态更新用 Mapper XML/注解更直观。项目优惠券查询用 MP，订单联表、并发更新和补偿抢占使用原生 SQL。

### 11.6 PageHelper 原理

`PageHelper.startPage` 通过 ThreadLocal 保存分页参数，MyBatis 插件拦截后续查询并改写 SQL，追加 limit，同时执行 count。注意它只影响紧随其后的第一条查询，使用不当会串页；请求结束也需要框架正确清理 ThreadLocal。

### 11.7 MySQL 事务 ACID 如何落到项目

- 原子性：订单更新与券更新一起成功或回滚。
- 一致性：状态机和唯一索引保证数据从合法状态到合法状态。
- 隔离性：并发支付/取消更新同一行时由锁和隔离机制协调。
- 持久性：提交后的订单、用户券和补偿记录可恢复。

### 11.8 MVCC 是什么

InnoDB 通过隐藏事务 ID、回滚指针、undo log 和 Read View 实现一致性读，让普通 SELECT 在很多情况下无需阻塞写操作。当前并发正确性不能只靠一次 SELECT 快照，最终仍靠加锁的条件 UPDATE。

### 11.9 当前会用到哪些锁

- UPDATE 订单或优惠券时对命中索引的记录加排他锁。
- 唯一索引插入会进行唯一性检查并发生必要的索引锁竞争。
- 条件更新应尽量走主键/唯一索引，减少锁范围。

订单支付/取消与领券主要依赖 DML 自动加锁，没有显式 SELECT FOR UPDATE；新增 AI 会话写入和知识版本更新则显式使用了 SELECT FOR UPDATE。不能把局部模块结论扩大到整个项目。

### 11.10 为什么使用 BigDecimal

`double` 是二进制浮点，许多十进制小数无法精确表示，连续计算会出现误差。金额用 `BigDecimal`，从字符串构造，使用 `compareTo` 比较，并统一数据库 `DECIMAL(10,2)` 精度。

`BigDecimal.equals` 会比较值和 scale，例如 `1.0` 与 `1.00` 不相等；业务大小判断用 `compareTo`。

### 11.11 索引为什么用 B+ 树

B+ 树层高低、磁盘 IO 少，叶子节点有序并串联，既适合等值查询也适合范围和排序。B 树非叶子也存数据，扇出较小；Hash 不支持范围和有序扫描。

### 11.12 本项目关键索引

- `coupon(status, receive_start_time, receive_end_time)`：可领取活动查询。
- `user_coupon UNIQUE(user_id, coupon_id)`：同模板每用户一次。
- `user_coupon UNIQUE(order_id)`：一张具体券最多绑定一个订单，也让一个订单最多绑定一张券。
- `user_coupon(user_id, status, valid_end_time)`：我的券与过期处理。
- `order_compensation_task UNIQUE(order_id, task_type)`：同类补偿任务幂等。
- `order_compensation_task(status, next_retry_time)`：到期任务扫描。
- `order_compensation_task(status, processing_time)`：僵尸任务回收。

### 11.13 联合索引最左前缀

联合索引从最左列开始匹配。`(status, next_retry_time)` 适合 `status=? AND next_retry_time<=?`。如果只按 next_retry_time 查询，通常不能充分利用该索引。

### 11.14 覆盖索引、回表、索引下推

- 覆盖索引：查询字段都在索引中，无需回主键索引取整行。
- 回表：二级索引找到主键，再查聚簇索引。
- 索引下推：存储引擎在索引扫描阶段先判断部分条件，减少回表。

### 11.15 如何排查慢 SQL

1. 慢查询日志定位 SQL。
2. `EXPLAIN` 看 type、key、rows、Extra。
3. 检查是否函数/隐式转换导致索引失效。
4. 检查联合索引顺序、回表量、排序和临时表。
5. 再考虑 SQL 改写、索引、批量查询、缓存和数据归档。

本项目历史订单先查订单，再循环查明细，存在 N+1 查询；订单量大时应批量按 order_id 查询明细后在内存分组，或联表后聚合组装。

## 12. Java 项目八股

### 12.1 HashMap 和 ConcurrentHashMap

- HashMap 非线程安全，JDK 8 是数组 + 链表 + 红黑树。
- 冲突链表达到阈值且数组容量足够时树化。
- ConcurrentHashMap JDK 8 主要使用 CAS + `synchronized` 控制桶级并发，读操作多数不加锁。

项目 WebSocket 连接表当前实际使用 HashMap，这是一项待修复问题。连接建立、关闭和群发可能并发发生；ConcurrentHashMap 可以解决映射结构的并发安全，但不能自动解决单个 Session 的发送顺序和复合业务操作原子性。

### 12.2 ThreadLocal 为什么可能内存泄漏

ThreadLocalMap 的 key 是弱引用，value 是强引用。key 被回收后，如果线程长期存活且没有清理，value 仍可能留在线程中。线程池线程尤其需要 `finally remove()`。

### 12.3 synchronized 和 ReentrantLock 区别

- synchronized 语法简单、自动释放，JVM 有多种优化。
- ReentrantLock 支持可中断、超时、公平锁、多个 Condition，但必须 finally unlock。

本项目没有用 JVM 锁控制优惠券，因为多实例下 JVM 锁无效；数据库条件更新直接在最终数据源处裁决。

### 12.4 volatile 能保证什么

保证可见性和禁止部分指令重排，不保证复合操作原子性。`count++` 即使用 volatile 也不是原子操作。

### 12.5 checked/unchecked exception 与回滚

RuntimeException 是 unchecked。Spring 默认对 RuntimeException 和 Error 回滚，对 checked exception 默认不回滚。本项目核心事务使用 `rollbackFor = Exception.class` 扩大回滚范围。

### 12.6 BeanUtils 的风险

- 同名不同语义字段也可能被复制。
- 包装类型 null 到基本类型可能触发拆箱问题。
- 客户端 DTO 可能覆盖服务端拥有的金额、状态和审计字段。

交易场景优先显式映射或 MapStruct 白名单映射。

## 13. HTTP、Nginx、接口设计八股

### 13.1 GET、POST、PUT、DELETE

- GET：查询，安全且应幂等。
- POST：创建或非幂等动作。
- PUT：整体更新或可幂等动作。
- DELETE：删除。

项目部分动作接口沿用了业务型 REST，如 `/coupon/{id}/start`。严格 REST 不是目标，关键是语义清晰、鉴权、幂等和状态校验。

### 13.2 幂等是什么

同一请求执行一次和多次，对系统最终状态影响相同。查询天然幂等；支付回调、取消、领券、创建订单需要专门设计。

实现方式：业务唯一键、幂等 token、状态机条件更新、请求号、去重表。项目支付重复确认和补偿任务唯一键都体现了幂等思想。

### 13.3 Nginx 在本项目做什么

- 托管管理端静态资源。
- `/api/` 反向代理到后端 `/admin/`。
- `/user/` 转发用户端请求。
- 转发 WebSocket Upgrade。
- 可进一步承担 TLS、压缩、限流、负载均衡和静态缓存。

### 13.4 为什么统一 Result 仍不等于 HTTP 状态码

当前业务异常通常返回 HTTP 200 + `code=0`，客户端按业务码判断。优点是前端处理统一；缺点是监控、网关和 HTTP 语义不够清晰。更规范可使用 400/401/403/404/409/500 等 HTTP 状态，并保留稳定业务错误码。

## 14. AI 客服专题：当前实现与扩展

### 14.1 当前链路

```text
小程序目前只发送 message
  → /user/ai/chat（后端支持可选 sessionId，身份取 JWT）
  → 短事务保存 USER 消息，会话置 PROCESSING
  → 事务外生成问题向量，查询启用且模型/维度匹配的知识
  → Java 全量候选余弦打分、阈值筛选、排序取 Top-K
  → 无命中：固定拒答；有命中：知识 + 最近20条消息调用模型
  → 短事务保存 ASSISTANT 消息，会话恢复 ACTIVE
  → 返回 sessionId 和 answer（前端尚未回传 sessionId）
```

安全点：API Key 只在后端；模型固定白名单；错误日志不打印 Key 和完整供应商响应；异常统一映射为服务不可用；提示词要求不泄密、不越权、不假装执行操作。

### 14.2 为什么提示词不能真正保证安全

模型提示词是概率约束，可能被提示注入绕过。真正的权限和数据边界必须在后端：

- userId 从 JWT 获取。
- 工具参数由后端构造或严格白名单校验。
- 模型只能建议调用工具，不能直接访问数据库。
- 敏感操作二次确认并审计。
- 输出经过敏感信息和业务规则校验。

### 14.3 RAG 怎么用于项目

当前实现将人工维护的知识条目向量化，连同模型名、维度和版本保存到 MySQL；问题向量与所有兼容的启用知识在 Java 中计算余弦相似度，按阈值过滤、排序取 Top-K。有命中就将标题和正文注入提示词，无命中直接返回固定人工客服提示。这是基础向量 RAG，不是关键词混合检索或向量数据库 ANN 检索。

后续可加入分块、关键词与向量混合检索、重排和引用；目前未向客户端返回证据引用。相似度达标不等于知识充分，仍需建立问答评测集和拒答策略。

动态价格、库存、订单状态不适合只放向量库，应通过 Tool Calling 实时查业务库。

### 14.4 Tool Calling 怎么防越权

例如模型请求 `getMyOrder(orderId)`：后端工具实现必须执行 `WHERE id=? AND user_id=当前JWT用户`，绝不接受模型或前端传来的任意 userId。取消订单等写操作还需校验状态、幂等和用户二次确认。

### 14.5 会话表为什么要 sequence_no 唯一索引

同一会话消息需要稳定顺序。`UNIQUE(session_id, sequence_no)` 防止同一序号重复；并发写入时还需原子分配序号，可锁会话行、使用独立计数器或数据库生成策略，不能简单 `select max + 1` 后无保护插入。

### 14.6 AI 服务如何降级

- 连接/读取超时。
- 限制输入长度和每用户请求频率。
- 熔断供应商异常。
- 高频固定问题走知识库模板，不必每次调模型。
- 模型不可用时返回稳定提示并提供人工入口。
- 记录耗时、token、错误码和回答质量指标，但日志脱敏。

## 15. 高频场景题与标准回答

### 场景 1：1000 人抢 100 张券，怎么保证不超卖

当前规模：MySQL 条件更新 `stock > 0` 原子扣减，影响行数决定成功；用户领取记录在同一事务插入；唯一索引防重复。

更大规模：入口限流 → Redis Lua 原子预扣 → 成功请求进 MQ → 消费端落 MySQL → 唯一索引最终兜底 → 失败补偿库存。必须设计库存对账，不能只相信缓存。

### 场景 2：支付和超时取消同时发生

两者都对同一订单执行带旧状态的条件 UPDATE，谁先提交谁赢；失败方影响行数为 0，不再处理券；订单和券更新处于同一事务，且访问顺序统一为先订单后券。

### 场景 3：支付接口超时，用户重复点击

前端防重复只改善体验，后端必须幂等。演示支付检测订单已支付且待接单时直接返回；真实支付用业务订单号/支付单号唯一键、回调状态机和平台查单保证幂等。

### 场景 4：优惠券核销失败怎么办

当前支付事务整体回滚，订单仍未支付，不产生混合状态。若真实支付平台已经扣款，不能简单回滚外部世界；需要支付回调记录、异常任务和人工对账，必要时补核销或发起退款。

### 场景 5：补偿实例执行到一半宕机

任务会停在 PROCESSING。扫描器把 processing_time 超过 10 分钟的任务恢复为 PENDING；不增加业务失败次数，因为不能确定业务本身失败。成功/失败更新还匹配本次 processing_time，旧实例不能覆盖新实例。

### 场景 6：定时任务部署多个实例会不会重复

候选查询可能重复，但 claim 条件更新只有一个实例成功。业务方法本身也应幂等。任务量更大时可引入分片调度、数据库 `SKIP LOCKED`、调度平台或 MQ。

### 场景 7：Redis 挂了怎么办

门店状态和菜单缓存会受影响。生产应让读请求有限回源数据库、配合限流防止把库打垮；门店状态需明确默认值还是拒绝服务；Redis 用主从/哨兵或集群，并监控命中率与故障。核心订单正确性当前不依赖 Redis，是一个优点。

### 场景 8：热门分类缓存刚过期，大量请求打来

缓存击穿。可用逻辑过期 + 单线程异步重建，或互斥锁只让一个请求回源，其余短暂等待/返回旧值；也可提前预热并给 TTL 加随机抖动。

### 场景 9：菜品改价后用户按旧价格下单

当前购物车保存加入时价格快照，提交时没有重新查菜品当前价，这是明确的改进点。生产应在提交时批量读取当前商品价格和起售状态，重新计价并提示用户价格变化；若业务允许短期锁价，则需记录报价版本和失效时间。

### 场景 10：订单号重复

当前“秒级时间 + 4 位随机数”在高并发下存在碰撞概率。应给订单号加唯一索引并在冲突时重试，或使用雪花 ID/号段服务/数据库序列，再编码成业务可读订单号。数据库主键仍可独立使用自增 ID。

### 场景 11：用户篡改 amount 为 0.01

后端忽略客户端金额，提交时按当前用户购物车和服务端费用配置重新计价，优惠券也由服务端查询；落库使用服务端生成的原价、优惠额和实付额。

### 场景 12：有人拿别人的订单 ID 查询详情或催单

不能只依赖“接口需要登录”。读取订单后还要比较资源 owner 与 JWT userId；不属于当前用户时按不存在处理。项目详情、再来一单、催单和取消都应走该校验。

### 场景 13：用户上传一个改名为 jpg 的脚本

不信任后缀和 MIME，服务端完整解码并识别真实图片格式，限制大小、边长、像素数和受控目录，服务端生成文件名。更高安全要求可重编码后再上传 OSS。

### 场景 14：JWT 被盗如何立即下线

纯无状态 JWT 在过期前难以立即撤销。可缩短 access token 有效期，引入 refresh token；Redis 保存用户 tokenVersion、黑名单或会话 ID；修改密码/封禁账号时提升版本，使旧 token 失效。

### 场景 15：ThreadLocal 为什么串用户

线程池复用线程，如果请求结束不 remove，旧 userId 会残留。应在拦截器 `afterCompletion` 或 Filter finally 中清理，并用测试覆盖异常请求路径。

### 场景 16：WebSocket 多实例怎么广播

本机内存连接表只能看到当前实例连接。用 Redis Pub/Sub 或 MQ 把通知广播到各 WebSocket 节点，每个节点只向本机目标连接发送；还需 sid 与登录身份绑定，避免伪造订阅。

### 场景 17：订单量大后历史订单很慢

先通过慢日志和 EXPLAIN 判断。给 `(user_id, status, order_time)` 建合适索引；避免 `select *`；消除订单明细 N+1，改为批量查询；深分页使用基于 `(order_time,id)` 的游标分页；冷热数据归档。

### 场景 18：补偿表越来越大

核心扫描索引保留 `(status,next_retry_time)`；SUCCESS 任务按时间归档/清理；MANUAL 建工单闭环；监控 PENDING 积压、最老任务年龄、成功率和重试次数；批量扫描使用稳定游标而不是无限 offset。

### 场景 19：AI 回答了错误价格或别人的订单

价格、库存和订单状态必须由受控工具实时查询；工具从 JWT 获取 userId 并做资源归属校验；模型不直接拼 SQL，不允许自带 userId；回答标注数据时间，工具失败则拒答而不是猜测。

### 场景 20：提示注入让 AI 泄露系统提示词

系统提示只能降低概率。后端不把 Key 和敏感数据放进上下文；知识检索做权限与来源过滤；工具使用白名单和参数 schema；输出做敏感检测；危险写操作二次确认；针对注入建立对抗测试集。

### 场景 21：是否应该上微服务

当前业务规模和团队规模下，模块化单体更简单，事务和运维成本低。出现独立扩缩容、团队边界、发布频率或资源隔离需求时，再按用户、商品、交易、营销拆分。拆分后必须面对分布式事务、调用超时、幂等、链路追踪和数据归属，不能为技术而拆。

### 场景 22：如果必须拆分优惠券和订单服务

不能再依赖一个本地事务。可采用 Saga/TCC 或可靠事件：订单创建后发锁券命令，营销服务幂等锁券；失败则订单取消；支付事件驱动核销；取消事件驱动释放；所有事件带业务 ID、版本和幂等记录，并有对账补偿。强同步接口也必须处理超时后的未知状态。

## 17. 项目缺点：高质量回答模板

不要说“项目没什么问题”。采用四段式：**现状 → 风险 → 当前取舍 → 改进**。

### 17.1 支付链路

> 当前为了先验证订单和优惠券状态流转，使用演示支付，由客户端接口触发确认。它不能代表真实资金结果。上线时我会增加支付单表，以微信验签回调为唯一成功依据，用订单号和平台交易号保证幂等；回调丢失时主动查单，并实现退款单、退款回调和日终对账。

### 17.2 ThreadLocal

> 当前通过 ThreadLocal 传用户 ID，但生产代码缺少请求结束后的统一 remove，这是我复盘出的风险。应在 afterCompletion 或 Filter finally 清理，并补异常路径测试。

### 17.3 缓存一致性

> 当前菜单用 Cache Aside，修改后删除缓存，适合单体低并发；但事务提交与删缓存时序还不够严谨。我会把失效动作注册到 afterCommit，并针对热点重建增加互斥或逻辑过期。

### 17.4 查询性能

> 历史订单存在逐单查明细的 N+1。小数据量下直观，但规模增大后应批量查明细并分组，同时给用户、状态、时间建立联合索引，深分页改游标。

### 17.5 订单号

> 当前订单号是秒级时间加四位随机数，可读但有碰撞概率。生产需要唯一索引和冲突重试，或改成雪花 ID/号段生成。

### 17.6 AI 客服

> 当前工作区已有后端会话持久化和基础向量 RAG，但前端还没把 sessionId 串起来；检索是 Java 全量候选计算，没有 ANN、混合检索、重排和证据引用，也没有实时订单工具。下一步先闭环前后端多轮和异常恢复，再补检索评测与受控工具，不能宣称已经实现生产级 Agent。

## 18. 测试怎么讲

### 18.1 测试分层

- 单元测试：Mockito 隔离 Mapper/第三方客户端，验证计价、参数和异常分支。
- Controller 测试：MockMvc 验证路径、JSON 契约、日期格式和返回结构。
- 数据库集成测试：真实 Mapper、唯一索引、事务和条件更新。
- 并发集成测试：多线程同时领券、支付和取消，验证最终状态集合。
- 端到端补偿测试：订单、用户券、补偿任务一起走到一致终态。
- 前端测试：Jest 验证管理端交互；Node Test Runner 验证小程序请求、登录态、支付防重和页面状态。

### 18.2 为什么只 Mock 不够

Mock 返回 `updateRows=1` 不能证明真实 SQL 条件、唯一索引、InnoDB 锁和 Spring 事务代理正确。并发一致性必须至少有真实数据库测试。

### 18.3 并发测试应该断言什么

不要只断言“没抛异常”，要断言业务不变量：

- 成功领取数不超过库存。
- 同用户最多一条用户券。
- 库存扣减数等于成功领取数。
- 支付/取消竞争后只能落入两个合法状态之一。
- 券更新失败时订单状态回滚。
- 多实例抢占只有一个成功。

### 18.4 测试数量怎么说

2026-08-30 历史实测：后端 115、管理端 53、小程序 125 个测试通过。2026-09-05 本次只进行了源码核对，没有重新运行测试；当前工作区新增了大量 AI 代码和测试，不能把上述数字当成当前分支验证结果。测试数量也不等于覆盖率、真实供应商联调结果或线上可靠性。
