# 优惠券与订单一致性设计

## 1. 功能目标

优惠券功能需要处理领取、锁定、核销和释放，并保证订单与优惠券在并发和异常情况下保持一致。

当前已实现的范围：

- 查询可领取优惠券、领取优惠券和查询我的优惠券。
- 服务端重新计算订单金额，不信任客户端传入的总金额。
- 下单时锁定优惠券，支付成功时核销，取消或超时时释放。
- 支付和取消并发竞争时，通过数据库条件更新保证只有一方成功。
- 超时取消长期失败时，记录独立补偿任务，进行有限次自动重试，最终转人工处理。
- 管理端创建、编辑、分页查询、开始发放、停止发放和删除草稿优惠券。

已支付订单退款链路尚未实现，因此当前不允许用户直接取消已支付待接单订单。

## 2. 为什么需要状态机

`coupon` 是优惠券模板，记录库存、门槛、优惠金额和活动时间。`user_coupon` 是用户领到的具体优惠券，保存领取时的金额和有效期快照，避免以后修改模板时影响历史数据。

| 状态 | 含义 | 可以进入的下一状态 |
| --- | --- | --- |
| `AVAILABLE` | 可使用 | `LOCKED` 或 `EXPIRED` |
| `LOCKED` | 已绑定待付款订单 | `USED`、`AVAILABLE` 或 `EXPIRED` |
| `USED` | 支付成功后已核销 | 终态 |
| `EXPIRED` | 已过有效期 | 终态 |

下单时不立即核销，而是先锁定。原因是订单尚未支付：如果直接核销，用户不付款或取消订单后会无故损失优惠券；如果不锁定，同一张券又可能被多个待付款订单重复占用。

## 3. 主要业务流程

### 3.1 领取优惠券

1. 根据当前登录用户和优惠券模板查询是否已领取，用于返回友好提示。
2. 通过带“发放中、在领取时间内、库存大于零”条件的 SQL 原子扣减库存。
3. 创建 `user_coupon` 快照记录。
4. 通过 `(user_id, coupon_id)` 唯一索引处理并发重复领取。如果插入冲突，整个事务回滚，之前扣减的库存也会恢复。

### 3.2 预览和提交订单

1. 后端根据当前用户的购物车、打包费、配送费和地址重新计价。
2. 优惠券门槛按菜品金额校验，最终实付金额由后端计算。
3. 订单保存 `original_amount`、`discount_amount`、`amount` 和 `user_coupon_id` 快照。
4. 订单插入后，使用带用户、状态、有效期、门槛和订单 ID 条件的 SQL 原子锁券。
5. 锁券失败时抛出异常，回滚订单、订单明细和购物车变更。

### 3.3 支付、主动取消与超时取消

支付与取消的共同原则是“先更新订单，后更新优惠券”，并且每条业务链路内的两次更新位于同一个事务中。固定访问顺序可减少死锁，同一事务可防止混合状态。

- 支付：只有当订单仍属于当前用户，且处于“待付款 + 未支付”时才能改为已支付；随后将绑定该订单的 `LOCKED` 优惠券改为 `USED`。
- 主动取消：验证订单归属后，只有“待付款 + 未支付”才能条件更新为已取消；随后释放优惠券。
- 超时取消：超过15分钟的待付款订单使用相同的条件更新。取消成功才释放优惠券；如果条件更新返回0，说明支付或其他状态变更已经先成功，取消方不再继续。

释放优惠券时必须同时匹配 `user_coupon_id`、`order_id` 和 `LOCKED` 状态。在有效期内恢复为 `AVAILABLE`，已过期则改为 `EXPIRED`。如果释放失败，订单取消事务整体回滚，避免出现“订单已取消，优惠券却永久锁在旧订单”的情况。

## 4. 并发一致性的核心

单纯的“先查询再修改”不能保证并发安全。支付线程和取消线程可能同时读到待付款，因此最终胜负必须由一条原子 SQL 决定。

```sql
-- 取消一方只能修改仍未支付的待付款订单
UPDATE orders
SET status = 6
WHERE id = ? AND status = 1 AND pay_status = 0;
```

先执行成功的一方会修改状态，后执行的一方条件不再成立，影响行数为0，因此不能再继续核销或释放优惠券。

最终只允许两类一致结果：

- 支付胜出：订单已支付，优惠券已使用。
- 取消胜出：订单已取消且仍未支付，优惠券已释放或过期。

## 5. 超时取消失败补偿

### 5.1 问题场景

强一致事务可以避免订单和优惠券出现混合状态，但不会让底层故障自动消失。例如优惠券绑定数据异常时，超时取消会因为无法释放优惠券而整体回滚，订单仍是待付款，优惠券仍是锁定。

无限重试不合适：瞬时故障需要留出恢复时间，永久数据异常却不会因为重试而消失；无限重试只会增加数据库、日志和运维压力。

### 5.2 最小补偿方案

| 状态 | 含义 |
| --- | --- |
| `PENDING` | 等待到期重试 |
| `PROCESSING` | 已被某个任务实例抢占 |
| `SUCCESS` | 订单问题已经解决 |
| `MANUAL` | 达到最大次数，需要人工处理 |

1. 首次超时取消失败后，使用 `REQUIRES_NEW` 独立事务保存失败原因和下次重试时间。这条记录不能与已失败的取消事务共用事务，否则会一起被回滚。
2. 同一订单和任务类型只有一条记录。重复记录时只刷新最近失败原因，不重置状态、重试次数或下次时间。
3. 原超时扫描通过 `NOT EXISTS` 跳过已进入 `PENDING`、`PROCESSING` 或 `MANUAL` 补偿流程的订单，避免绕过5分钟间隔和最大重试次数。
4. 补偿任务每分钟第30秒扫描一次，单批最多100条；只查询已到期的 `PENDING` 任务。
5. 执行前使用条件更新将 `PENDING` 改为 `PROCESSING`。多实例同时竞争时，只有影响行数为1的实例获得处理权。
6. 补偿重新执行完整的 `cancelTimeoutOrder`，而不是单独释放优惠券。
7. 失败后间隔5分钟再试；第3次自动补偿仍失败时改为 `MANUAL`。每条任务独立处理，单条失败不影响其他订单。
8. `PROCESSING` 超过10分钟无结果时恢复为 `PENDING`，不计入业务重试次数。`processing_time` 同时作为持有权标识，防止旧执行者覆盖已被新执行者接管的任务。

`SUCCESS` 表示订单问题已经解决，不要求本次执行一定取消订单。例如补偿执行时订单已经支付，超时取消会幂等返回；此时不再需要取消订单，补偿任务可以标记为成功。

## 6. 接口

### 6.1 用户端

所有“我的优惠券”、下单、支付和取消操作都使用登录上下文中的当前用户 ID，不接受前端任意指定用户 ID。

| 方法 | 路径 | 作用 | 关键参数 |
| --- | --- | --- | --- |
| `GET` | `/user/coupon/list` | 查询当前可领取的优惠券 | 无 |
| `POST` | `/user/coupon/{couponId}/receive` | 领取优惠券 | 路径参数 `couponId` |
| `GET` | `/user/coupon/my` | 查询当前用户的优惠券 | 无 |
| `POST` | `/user/order/preview` | 获取服务端计价和预计送达时间 | `addressBookId` |
| `POST` | `/user/order/submit` | 提交订单并可选锁定优惠券 | `addressBookId`、`payMethod`、`userCouponId` 等 |
| `PUT` | `/user/order/payment` | 模拟支付并核销优惠券 | `orderNumber`、`payMethod` |
| `PUT` | `/user/order/cancel/{id}` | 取消当前用户的未支付订单 | 路径参数订单 ID |

提交订单时，前端传入的 `amount`、`packAmount` 和 `estimatedDeliveryTime` 仅为兼容旧客户端，后端会忽略这些值并自行计算。

### 6.2 管理端

| 方法 | 路径 | 作用 | 状态限制 |
| --- | --- | --- | --- |
| `POST` | `/admin/coupon` | 创建优惠券 | 服务端固定创建为草稿 |
| `GET` | `/admin/coupon/page` | 分页查询优惠券 | 无 |
| `GET` | `/admin/coupon/{id}` | 查询优惠券详情 | 无 |
| `PUT` | `/admin/coupon/{id}` | 编辑优惠券 | 仅草稿 |
| `PUT` | `/admin/coupon/{id}/start` | 开始发放 | 仅草稿，且库存和时间条件合法 |
| `PUT` | `/admin/coupon/{id}/stop` | 停止发放 | 仅发放中 |
| `DELETE` | `/admin/coupon/{id}` | 删除优惠券 | 仅草稿 |

## 7. 测试与验证

当前完整 Maven 测试结果为：`96 tests`、`0 failures`、`0 errors`、`BUILD SUCCESS`。

与本模块直接相关的验证包括：

- 并发领取时单用户只能成功一次，库存不会超扣。
- 锁券、核销和释放都校验用户、订单绑定和当前状态。
- 支付与超时取消真实并发竞争，连续执行5次，只能得到两种一致状态。
- 支付与用户主动取消真实并发竞争，连续执行5次，不会产生“已取消 + 已支付”。
- 优惠券核销失败时支付回滚，释放失败时取消回滚。
- 补偿任务的到期查询、原子抢占、有限重试、转人工、超时回收和旧执行者防护。
- 补偿端到端执行后，订单、优惠券和补偿任务同时进入一致结果。
- 真实 Spring 代理和数据库环境下，外层事务回滚后 `REQUIRES_NEW` 补偿记录仍然提交成功。
