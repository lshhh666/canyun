## Java 后端实习 / 校招推荐版

以下五条是项目段候选正文，可按版面压缩为四条。本人需确认职责归属，时间和团队信息不由代码推断。

- **订单与优惠券一致性：**将订单计价收口到服务端并保存金额快照；以库存条件更新、联合唯一索引和本地事务处理并发领券，利用订单状态条件更新协调支付与取消，保证对应订单与券核销/释放共同提交或回滚。
- **异常补偿：**针对超时取消失败，采用独立事务记录补偿任务，通过条件更新抢占、定时重试和超时回收恢复执行；达到失败上限后转为待人工处理状态，避免持续失败无限重试。
- **受控 AI 客服：**结合向量检索、问题改写与证据充分性判断实现规则问答，并接入当前用户订单、详情及优惠券资格查询；身份从登录上下文获取，金额和状态由 Java 确定性生成，取消操作经用户二次确认后执行。
- **知识更新与任务恢复：**将知识新版本和向量任务同事务保存，模型调用在事务外执行，仅启用且向量就绪的知识参与检索；通过有限退避重试、超时回收及执行令牌校验处理任务失败和迟到回写。
- **反馈处理闭环：**贯通用户负反馈、关联知识复测和人工确认，保存回答与实际知识版本，确认正确后关闭反馈；真实 MySQL 并发测试验证两个管理员同时提交只创建一条复测任务，已有页面验收覆盖确认错误后重新复测的分支。

## 版面只能放四条时

将前两条合并为：

> 设计服务端计价与优惠券全链路，通过库存条件更新、联合唯一索引和本地事务处理并发领取与支付/取消竞争；针对超时取消失败建立独立补偿任务，支持抢占、有限重试与超时回收。

再保留受控 AI 客服、知识任务和反馈闭环三条。

普通 Java 业务岗保持交易条目优先；AI 应用后端岗可将受控客服、知识任务移到前面。具体取舍应匹配目标岗位 JD。

## 需要突出会话并发时的替换条目

> 实现 AI 多轮会话持久化及历史恢复，通过会话行锁、处理轮次和截止时间控制并发；提问与回答分别在短事务中保存，模型调用放在事务外，超时后由后续请求接替并按轮次拒绝旧结果写入。

这一条可替换异常补偿条目，适用于更侧重 AI 会话工程的岗位。会话使用轮次序号，后台任务使用 processing_time，不要在面试时混成同一种令牌。

## 面试时需要解释的范围

1. 当前检索将兼容向量加载到 Java 中计算余弦相似度，属于小型知识库精确检索方案。
2. 复测使用管理员关联的知识并复用最终回答生成器，不经过线上完整检索、问题改写和工具路由，因此复测通过不能直接证明线上召回正确。
3. 知识更新先停旧版本，新版向量未就绪期间存在该知识暂不可检索的窗口；设计优先避免继续提供已修正的旧规则。
4. 补偿的“待人工处理”是任务终态，不声称已有完整人工工单平台。
5. 支付按个人项目范围采用演示流程。介绍支付/取消竞争时说明这一前提即可，不需要为此继续扩充项目才能投递。
6. 交易一致性描述针对已核查的用户支付、未支付取消和券链路，不扩大到所有管理端订单流转。
7. “负责/设计/实现”需与本人实际工作相符；已有模板和基础代码不写成完全从零原创。
